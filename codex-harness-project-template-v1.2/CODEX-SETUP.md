# 给 Codex：新项目接入步骤

这是用户可明确调用的接入说明，不是已安装的插件或后台服务。用户让你按本文件接入项目时，完成以下工作；用户不需要自行搬运协议对象。不要要求安装额外技能，核心规范和提示词均在本包。

## 1. 确认入口，先保留原现场

从用户提供的三个路径定位目标项目、规范模板包和执行器包；用户已提供的路径不重复询问。读取有效 AGENTS.md 和 Git 状态，识别现有未提交改动。项目有 CodeGraph 索引时先用 CodeGraph 理解代码，不自动建索引。

规范复制和分析不依赖模型 Key 或项目构建环境，可以先完成。不要因为 doctor 暂不可用而把全部接入工作停在“等配置”。真实项目命令和工作 AI 派发必须等待预检通过。

## 2. 把模板合并到项目

- 将本包 `project/docs/harness/` 复制到项目 `docs/harness/`。相同文件可以跳过；已存在且内容不同的文件先比较、保留项目内容，只合并需要更新的部分，不能递归覆盖已有任务、进度或规则。
- 读取 `project/AGENTS.fragment.md`。若根 AGENTS.md 不存在，以片段创建；若已存在，在保留原内容的基础上合并标记块。已经有 CODEX_HARNESS_START/END 块时先比较，不重复追加，不覆盖用户自定义规则。复制后核对链接。
- `protocol-v1` 是固定版本规范原件；核对 `protocol-source.json`，项目定制放在外层文档。模板中的模拟示例和 REPLACE 字段不能当作业务运行状态。
- 记录接入改动，不自动 git init、清理用户改动、提交或推送。只接入新项目时，不从其他项目复制画像、凭据和运行历史。

## 3. 回填项目事实

读取实际依赖、构建、CI、入口、相关实现和现有测试；回填 project-profile.md。缺少依据的部分写“待确认”，区分静态观察、实际执行和推断。不要因为检测到某语言就声称架构已分析。

补齐项目路径、用途、技术栈、模块和真实文件依据、适用规则、基线、测试方法、外部服务及权限范围。缺少业务需求时，只做接入与画像，不生成虚构功能。

## 4. 建立项目外的本机配置

使用 `project/docs/harness/config/harness.config.example.yaml` 生成项目外的本机配置；记录其绝对路径到用户可见的交接说明。每个项目独占 work_root/control_root，三者与 source_root 互不包含。模板包和执行器也不要塞进受控源码工作目录。

填入本机执行器和 Codex CLI 路径。使用 `node --version`、`git --version` 和实际工具帮助核对能力；缺 Node.js 24、Git、CLI 或项目运行时则明确报告缺项，不假设桌面应用自带的一切都可由命令调用。不要擅自安装全局软件或改变系统配置。

API 地址和模型名由用户配置或提供。Key 只让用户在项目外私有文件填入；不要读取私有文件到模型上下文，不打印任何 Key。只使用 primary 时可删除备用配置；使用多个时分别命名并记录选择，不自动切换。

按已核实的项目环境生成本机启动入口，可参考执行器包 `examples/harness-project.cmd`。只为进程设置必要运行时变量，不带入旧机器路径。项目语言运行时与执行器 Node.js 24 独立，必要时使用 Node 24 的绝对路径启动 dist/harness.mjs。

将 AGENTS.md、docs/harness/ 与独立验收脚本列入 protected_paths。按项目实际情况登记命令：id、固定 argv、cwd='.'、timeout_seconds、purpose。初始化依赖需 purpose=init；不得先注册虚构的 npm test 或忽略现有失败。

## 5. 预检、初始化和任务闭环

阅读执行器 README.md、COORDINATOR.md 和 VALIDATION.md；历史宿主失败不代表当前机器结果，需要当前 doctor --live 实测。配置缺失、接口不兼容、沙箱失败时保存原因，不添加跳过检查的参数。

配置可用且预检通过后，首次 init --project；已有状态先 status。让执行器收集事实、创建隔离 worktree/副本，再补充项目分析、登记命令并运行 baseline。跟踪已有失败和当前需求问题，不能以空基线宣称可信验证已完成。

随后按项目 docs/harness/COORDINATOR.md 和执行器命令约定生成需求文档、冻结输入、run、verify、inspect、decide，失败时自动形成返工单。三份文档、评审和协议对象均由 Codex 维护，不要求用户逐轮传话。

## 6. 接入完成时说明

向用户报告项目规范入口、本机配置与私有文件位置、实际检查结果，以及下一步可执行动作。明确区分“模板已入库”“环境已通过”“业务已验收”三个结论。报告时只展示路径和变量名，不展示密钥。

如果项目已经接入且只是换电脑，保留仓库规范，重新生成本机绑定；旧运行没有完整控制记录和候选时按新任务启动，不冒称恢复。

## v1.2 本机策略与验收

采用模板中明确声明的 trusted_local + network:true 模式：普通读取与联网允许，指定控制/原项目/私有密钥/Codex 目录拒绝访问；不自动修改防火墙。此模式适用于用户信任的项目。老 strict 配置不静默转换。项目命令仍进原生沙箱；Codex 外层沙箱无法嵌套启动时，只对可信协调者 CLI 申请宿主执行。

构建输出用 generated_dirs，源码和标准不能被排除。项目命令所需可写缓存放检查副本，并按实际工具登记固定初始化命令；初始化不能改动源码。登记 required/role 的真实测试产物，核对用例数；退出0和执行器自动摘要都不能替代业务通过。inspect 分页日志必须读全。
