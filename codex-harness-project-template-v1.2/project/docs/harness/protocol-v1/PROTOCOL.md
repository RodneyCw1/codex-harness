# 交换协议与状态提交 v1

## 1. 编码、版本和可信来源

交换格式为 UTF-8 JSON，协议版本为 `1.0`。字段使用 snake_case，枚举区分大小写。机器对象结构由 [contracts.schema.json](schemas/contracts.schema.json) 定义，配置结构由 [config.schema.json](schemas/config.schema.json) 定义。未知字段按当前版本拒绝；协议变更须升级版本并同步双方。

`artifact_mode` 为 `illustrative` 或 `live`。本包所有示例和空状态模板均为 illustrative。真实运行必须拒绝示例数据；不能只改这个字段就把示例变成实际证据。

schema 只验证结构。消息 ID、`producer`、`kind` 不能证明消息身份。执行器必须通过真实调用通道识别 Codex、执行 AI 和验证进程，并将写权限分开。执行者即使输出符合 review schema 的 JSON，也不能写入评审通道。

## 2. 公共标识与引用

| 字段 | 语义 |
|---|---|
| protocol_version | 交换格式版本，与业务规范版本不同 |
| kind / message_id | 对象类型与不可复用的消息ID |
| task_id / feature_id / batch_id | 需求任务、当前功能、执行批次 |
| spec_version / spec_digest | Codex冻结的业务规范整数版本与内容摘要 |
| submission_id / round_number | 候选唯一提交与该功能本批次的提交轮数 |
| snapshot_id | 代码输入快照的内容摘要；不能用未提交改动之前的HEAD替代 |

ID 在对应任务内唯一。重复 message/submission 必须内容一致才可作为幂等重送；同 ID 内容不同应拒绝并报告冲突。UTC 时间格式为 `YYYY-MM-DDTHH:mm:ssZ`，执行器还必须验证日期真实有效、结束不早于开始。

所有摘要格式为 `sha256:` 加64位小写十六进制。路径引用以当前批次的受信数据根为基准；`allowed_paths`、`protected_paths` 和命令 `cwd` 则以候选项目根为基准。引用必须存在、解析后仍在允许根内，不能通过 `..`、绝对路径或链接逃逸。

### 快照与规范摘要

真实代码快照使用不可变文件清单：`files` 内逐项记录根相对路径、文件内容SHA-256和执行权限标志，另列 `excluded_paths` 及排除原因。覆盖源代码、项目配置、锁文件、必要未跟踪文件和实际使用的子模块/资源。缓存和生成物只能在确认不属于运行输入后排除；禁止遗漏实际影响测试的文件。

清单文件以UTF-8无BOM编码，对象键按字典序，数组中的文件按路径排序，JSON无额外空格并以一个LF结尾。`snapshot_id` 是该清单文件原始字节的SHA-256。文件内容和规范原始字节不进行换行或空白标准化。执行器保存清单及可恢复的真实文件，并在验证前后重新核对。

`spec_digest` 对规范文件路径和内容摘要组成的排序清单采用同样编码计算。必须包含实现、验收、测试文档、官方测试/验证入口及冻结命令注册表。示例的manifest仅覆盖示例文件，不能当成真实项目快照。日志等运行产物不进入代码输入快照。

## 3. 对象合同

| kind | 写入来源 | 关键内容 |
|---|---|---|
| task | Codex，经执行器冻结 | 目标、规范与基线、当前快照、文档、AC/TC追踪、命令、范围、上轮返工 |
| execution_report | 执行者提交，执行器核对 | 唯一提交、轮数、快照、真实改动、自测引用和未解决问题 |
| verification_evidence | 受信验证进程 | AC/TC、快照、规范、环境、实际命令、时间、结果、退出码及原始产物摘要 |
| review | Codex评审通道 | 逐项结论、硬门槛、阻断项、总体结论和下一步 |
| rework | Codex，经执行器冻结 | 原结论与提交、缺陷、期望与实际、复现、范围及复验 |
| feature_list | 执行器按Codex决定提交 | 功能依赖、状态及对应通过结论、快照和证据 |
| run_state | 执行器 | 运行状态、阶段、计数、状态版本、恢复事件和未决操作 |

### 任务包 task

`acceptance_criteria` 关联需求和测试ID，`test_cases` 关联AC和命令ID。所有ID必须唯一且引用闭合；每个必需AC至少有一个用例。具体方案由文档给出，`context_refs` 保存只读上下文及摘要，执行器应保证执行 AI 能实际取得这些内容，而不只给无法访问的本机路径。

`expected_round` 指下一次候选提交轮数。任务修订不能偷偷重置轮数。代码执行任务的 `scope=feature`，轮数从1开始，允许路径非空。当前代码必须等于 `current_snapshot`，原始基线保存在 `baseline_snapshot`。

最终验收使用相同task结构，但 `scope=final`、`feature_id=FINAL`、`expected_round=0`、`allowed_paths=[]`。它是供Codex和验证器使用的只读验收包，汇总全部必需AC、最终用例及命令，不派发给执行AI写代码。

### 执行报告 execution_report

所有内容均视为待核实。候选提交时由执行器分配稳定 `submission_id`，从文件系统核实 `changed_files` 和 `snapshot_id` 后保存报告，禁止模型随意指定下一轮数或快照冒充新提交。

`self_test_refs` 只能解释自测情况；没有独立证据时不得转成通过。提交后必须停止对该快照的修改。执行者还在写入时不能开始官方验证。

### 验证证据 verification_evidence

一个对象对应一个TC的结果，包含关联AC、实际命令、环境ID、起止时间和至少一个产物。多个TC可以来自同一次测试命令，但日志必须分别定位结果。AC需要多个TC时须全部具备通过证据。

`result=pass` 至少要求退出码为0、预期断言成立、所需类型产物存在且摘要一致。退出码为0本身不等于行为成立。`error` 表示环境/运行故障，`unverified` 表示未能执行；二者都不能支撑通过。

证据必须由受信验证进程产生，原始日志不可由执行者覆盖。执行器检查任务、功能、批次、提交、规范摘要、快照、环境和命令注册表均匹配。正式通过不能引用另一轮或另一阶段证据。

### 评审 review

`checks` 按AC列出 `pass / fail / unverified` 和证据引用，不能省略必需项；可选项可以列出，或在summary中披露限制。`hard_gates` 对应范围、标准完整及交接准备；`unresolved_blockers`列出仍需解决的问题。

- ACCEPT：所有必需AC通过，全部硬门槛为true，阻断项为空；feature阶段的下一步是next_feature（没有剩余功能时转入最终验收），final阶段是deliver。
- REVISE：下一步rework，必须引用返工单；缺陷和失败AC有对应证据。
- BLOCK：下一步pause，必须说明具体阻塞原因；可保存已完成的部分验证。

review用于已经冻结候选后的评审。提交前的鉴权、环境、权限或信息阻塞由Codex确认后直接记录run_state的paused和stop_reason，并将已选择功能记为blocked；不能伪造候选或测试证据。候选后的检查未能执行时保存实际失败诊断作为unverified/error证据。执行器遇到拒绝或故障立即停止相关操作，不等待模型批准才停止。

可选AC的失败可以作为非阻断限制记录；它不能掩盖必需AC失败。ACCEPT的结构校验不检查AC是否必需，这一步必须按冻结任务包进行语义校验。

final证据与review使用 `feature_id=FINAL`、`round_number=0` 和独立最终验收提交ID。最终检查不新增功能返工轮数；发现回归后对受影响功能继续计数。最终ACCEPT还须确认全部功能状态通过、最终必需用例齐全。

### 返工单 rework

`source_review_id`、`source_submission_id` 必须指向本任务有效REVISE，`next_round` 必须为原功能提交轮数加1。每个缺陷列出AC、实际与期望、证据、复现、修复范围和复验TC。范围须在Codex冻结的授权范围内，不能通过返工单绕过任务边界。

### 状态 feature_list / run_state

功能通过时必须有 `approved_snapshot_id`、`acceptance_review_id` 和证据引用，空模板不能通过。依赖图不得循环，所有依赖ID必须存在。同一任务最多一个功能in_progress。

`run_state.revision` 是持久化版本。`counters` 为每个功能独立记录本批次提交数、历史累计数、连续无进展数、当前已验证通过项和已关闭缺陷。计数从提交和评审事件计算，不能采信执行者传来的计数。

## 4. 通过闸门的检查顺序

1. 核验调用来源、协议版本和 `artifact_mode=live`。
2. 执行JSON Schema校验，拒绝不合法数据。
3. 检查ID、阶段、轮数、依赖、AC/TC/命令引用及状态前置条件。
4. 核对冻结规范、候选、命令注册表和环境；检测受保护文件变化。
5. 检查实际产物存在、摘要一致、日志与断言支撑对应结论。
6. 确认必需AC的所有TC均通过，无阻断项、没有降低标准。
7. 按状态机和轮次规则提交结果。最终completed另需最终ACCEPT。

任何一步不成立都不得把功能标为passing。第1步也说明：通过schema不等于具有审批权限。

## 5. 持久化与恢复

执行器为项目取得单写入锁。所有状态更新附带预期revision，冲突时重新读取，不覆盖更新。先将事实事件和产物写入受信存储，再提交包含review与状态的原子事务；若使用文件，使用临时文件、原子替换及可恢复事件日志。进度摘要在权威状态提交后生成。

每次可能产生副作用的工具操作记录 `operation_id`、参数摘要、前置快照、调用/响应关联、状态及副作用引用。调用前写intent；完成后写结果。崩溃发生在两者之间时标记unknown，先检查文件或进程实际状态，确认已完成则复用结果，否则由Codex决定补偿或重新执行。

HTTP重试不增加提交轮数，也不能重放已经完成的工具操作。相同模型调用ID在不同请求中不保证全局唯一，必须使用执行器自己的操作ID和参数/前置快照关联。

取消和暂停保留证据及候选。续跑必须核对源项目是否变化；不能静默把旧结果应用到新基线。中断恢复不重置预算，明确续跑暂停任务才能建立新批次。

## 6. 结构校验之外的实施义务

schema不负责鉴权、真实文件访问、路径隔离、摘要计算、原子事务、执行测试、证据真实性或重试去重。实现者必须完成上述语义校验，并用 [验收场景](examples/acceptance-scenarios.md) 在真实执行器上验证。本包只对文档、数据结构及规则推演进行交付检查。
